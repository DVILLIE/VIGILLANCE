# D'Vielle — Project Charter and Product Strategy

Version 1.0 • 10 October 2026 • Proposed baseline for owner review

## Purpose and intended outcome

D'Vielle — Intelligent Vigilance / Vigilia — Always Watching is intended to make ordinary computer and internet use safer and less stressful. The core product will remain free to end users. The project will combine explainable security observation, narrowly authorized protection, recovery and optional ethical assessment of assets the user owns or is authorized to test.

The primary outcome is preserved user work: fewer consequential compromises, fewer unnecessary interruptions and demonstrable recovery when something goes wrong. Adoption is an outcome of usefulness, trust and accessibility, rather than a substitute for evidence of protection.

## Product principles

The product operates locally by default. It explains consequential actions using observed evidence, not invented certainty. It preserves existing antivirus and administrator policies. It separates inference from authority, records changes durably and checks whether the intended effect actually occurred. Unsupported or unavailable capabilities are visible to the user. Decoration, reputation scores and AI fluency are never presented as protection evidence.

Automatic operation means exercising specific authority the user has already granted. It does not mean silently expanding permissions, downloading arbitrary tools or rewriting unrelated application configuration.

## Scope and product structure

The Everyday Guardian provides device posture, process/network observations, prioritized findings, explicit action policies, independently verified containment, owned-change recovery and a understandable work log. The Ethical Assessment Workspace adds scoped inventory and assessments, signed scope records, rate limits, evidence export and reports. Offensive tests require explicit target authorization and a dedicated execution boundary.

Initial delivery concentrates on protected installation, authenticated privileged operations, durable recovery and process network restriction. Later increments introduce evidence graphs, calibrated inference, cryptographic inventory, supported migration adapters and optional assessment connectors.

Mobile operating systems, custom kernel drivers, arbitrary firmware repair and unrestricted autonomous exploitation are separate proposals. Their exclusion from the first delivery is a sequencing decision: they require different platform boundaries and validation, not a claim that future solutions are impossible.

## Governance and authority

The human project owner decides product direction, accepted automatic actions, publication and deployment. Engineering implements reviewed contracts. Security review challenges privilege, identity and recovery assumptions. Quality review evaluates reproducible evidence. Privacy review verifies data flows and retention. These are responsibilities; this document does not claim that a staffed team has already been appointed.

Application implementation remains awaiting joint agreement. This documentation task authorizes documentation only.

## Success and adoption

Measure prevention and missed attacks by declared attack-path class; false interventions by benign task and user hour; recovery correctness; user task completion; total process-tree resource use; privacy leakage; accessibility and installation success. Publish operating-system/build prerequisites and test scope with results. Compare against declared free baselines under identical workloads before making superiority claims.

Build adoption through clear onboarding, quiet defaults, multilingual expansion after English terminology stabilizes, shareable redacted reports, transparent changes and community participation. Do not purchase trust through fear messaging, fake testimonials or intrusive telemetry.

## Sustainability

Free distribution still requires maintenance, release signing, hosting and response effort. Prefer local computation, cacheable static signed artifacts, community mirrors and optional donations or sponsorship without selling private telemetry. Core protection must remain usable without a cloud account. Any future service must have a separate privacy/data-flow review.

Operational cost is modeled as fixed release/maintenance cost plus users × update frequency × bytes transferred, plus support effort. No budget or funding has been verified. Measure these quantities during controlled rollout before promising unlimited hosted services.

## Milestones and completion

The delivery sequence is defined in [Step-by-Step Implementation Plan](17_Step_by_Step_Implementation_Plan.md). Each milestone ends with evidence and a release decision. Documentation completion is distinct from source completion, host deployment and product validation. [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) supports integrating security throughout development; it does not certify this project.
